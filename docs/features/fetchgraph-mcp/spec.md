# FetchGraph Retrieval API и MCP v1 — контракт реализации

**Результат для пользователя.** Пользователь один раз связывает именованный источник и модель с MCP-сервером. Затем в Codex, OpenCode или другом MCP-клиенте задаёт вопрос, например «Сколько заказов в магазине?». FetchGraph строит запрос по схеме и возвращает данные с выполненным планом и происхождением. Внешний агент продолжает рассуждение по EvidenceBundle. Convenience-вызов answer добавляет синтез ответа со ссылками на наблюдаемый результат. В контекст внешнего агента попадают краткий ответ и несколько выдержек. По ссылке агент может проверить число без повторного inference.

Статус документа — реализованный контракт. Нормативные имена, типы, обязательность и границы полей всех четырёх инструментов приведены в [tools.json](tools.json). Числовые бюджеты ниже — начальные продуктовые решения v1. Сервер обслуживает один клиентский процесс по stdio. Один вопрос адресован одному логическому источнику. Вопрос по объединённому набору данных можно адресовать заранее собранному composite-провайдеру.

## Самостоятельный Retrieval API

Основная операция — retrieve(question) → EvidenceBundle. Для Python установить extra retrieval. Конфигурация источников и inference общая с MCP.

```python
from fetchgraph import FetchGraph, retrieve, answer

graph = FetchGraph("/srv/shop/fetchgraph.toml")
bundle = graph.retrieve("Сколько заказов в магазине?", source="shop")
print(bundle.evidence[0].data)  # {"n": 1000}
print(bundle.plan.context_plan[0].selectors)

# Функции уровня модуля принимают тот же config.
bundle = retrieve("Сколько заказов?", config="/srv/shop/fetchgraph.toml")
result = answer("Сколько заказов?", config="/srv/shop/fetchgraph.toml")
print(result.answer)
print(result.bundle.evidence[0].data)
```

При единственном настроенном источнике Python-вызов может опустить source. При нескольких источниках передать source явно, иначе INVALID_ARGUMENT до обращения к inference. Для вызова fetchgraph.retrieve(question) без config задать переменную окружения FETCHGRAPH_CONFIG с путём к TOML. Глобальный изменяемый default client отсутствует. Созданный FetchGraph хранит свою конфигурацию. В асинхронных приложениях использовать await graph.aretrieve(...) и await graph.aanswer(...), один event loop на экземпляр. Синхронный метод внутри активного event loop выдаёт RuntimeError с указанием async-метода.

| Поле EvidenceBundle | Контракт |
|---|---|
| plan | Существующая модель Plan с нормализованными и фактически переданными fetch селекторами. Пустой context_plan означает отсутствие допустимой операции. У пустой выборки plan сохраняется. |
| evidence | До восьми записей ref, source, locator, text, data, provenance. data содержит JSON-совместимый исходный результат, включая числовые агрегаты и строки. text — выдержка для LLM. Для текстовых документов или не представимого в JSON пользовательского объекта data может быть null. |
| sources | Логические id и kind источников, к которым относится запрос. |
| diagnostics | status, profile, gaps и llm_calls. complete означает полученные свидетельства без известных ограничений, partial — известные ограничения, insufficient — отсутствие свидетельств. llm_calls относится к retrieval и в текущей реализации равен 1. |

Provenance содержит source, locator, selectors и retrieved_at — время наблюдения по серверу в UTC. Селекторы соответствуют выполненному плану, включая серверные limit/offset. Данные bundle можно сохранить через model_dump_json() и восстановить через EvidenceBundle.model_validate_json(). Отметка времени фиксирует момент получения, версия изменяемого внешнего источника при этом неизвестна.

retrieve заканчивается после PLAN → FETCH. answer добавляет SYNTH и возвращает AnswerResult(status, answer, gaps, bundle). gaps в AnswerResult учитывает также ограничения синтеза, а диагностика bundle описывает retrieval. Прежний MCP fetchgraph_ask сохраняет формат ответа. Существующие BaseGraphAgent/create_generic_agent остаются отдельными публичными точками интеграции.

RetrievalError экспортируется из fetchgraph и предоставляет code/retryable с теми же кодами, что у MCP. Ошибки загрузки конфигурации относятся к конструированию клиента. Python bundle содержит данные целиком в пределах бюджета и самодостаточен. В MCP ref позволяет дополнительно прочитать сохранённый текст до истечения TTL.

## Запуск и конфигурация

Добавить extra `mcp` с Python MCP SDK и клиентом OpenAI-compatible API, entry point `fetchgraph-mcp`. Из checkout установка `python -m pip install '.[mcp]'`. Запуск `fetchgraph-mcp --config /absolute/path/fetchgraph.toml`. Опция `--check-config` проверяет той же функцией конфигурацию, ссылки, наличие файлов и переменных окружения, доступность фабрик, выводит итог в stderr и завершается. При успехе код 0, при ошибке конфигурации 2. При обычном запуске проверить конфигурацию до initialize. Данные и inference загружать лениво.

Пример полного рабочего профиля для локальной модели. Пользователь подставляет идентификатор, под которым модель уже обслуживается его endpoint, и располагает TOML рядом с каталогом `_demo_data`.

```toml
version = 1

[profiles.local]
base_url = "http://127.0.0.1:8080/v1"
model = "local-instruct"

[sources.shop]
kind = "csv"
description = "Заказы, покупатели и товары магазина"
data_dir = "_demo_data/shop"
schema = "_demo_data/shop/schema.yaml"
inference_profiles = ["local"]
default_profile = "local"
```

Грамматика TOML закрытая. Все поля примера обязательны для соответствующих типов. Дополнительные допустимые поля профиля — `api_key_env` (имя переменной окружения), `plan_model`, `synth_model` (непустые строки). Переопределения стадий имеют приоритет над `model`. API-ключ для удалённой модели задаётся, например, как `api_key_env = "FETCHGRAPH_MODEL_KEY"`. Отсутствующая или пустая указанная переменная — ошибка конфигурации. Если поле опущено, запрос посылается без credential. URL абсолютный, HTTPS либо HTTP на loopback, без userinfo, query и fragment. Для удалённой модели выбирают разрешённый для данного источника профиль осознанно — ему передаются вопрос, метаданные схемы и выбранные выдержки.

От 1 до 32 источников и от 1 до 8 профилей. Идентификаторы и длина description соответствуют tools.json. У каждого источника непустой список уникальных существующих профилей и default_profile из него. Пути разрешаются относительно TOML, независимо от рабочего каталога клиента. Конфигурация изменяется перезапуском процесса.

| kind | Дополнительные обязательные поля | Привязка |
|---|---|---|
| csv | data_dir, schema | Загрузить SchemaConfig в формате JSON из файла с любым расширением (демо schema.yaml содержит JSON). Использовать build_pandas_provider_from_schema. Каждый CSV внутри data_dir, включая разрешение симлинков. |
| sqlite | database, schema | Та же SchemaConfig, существующий файл SQLite, отдельное соединение на запрос с URI mode=ro и query_only. Использовать build_sql_provider_from_schema, закрывать соединение в finally. |
| artifact | run_dir, run_id | Один конкретный каталог прогона и его непустой логический ID. Пайплайн archgraph_v1. В v1 гарантирован формат JSON-объектов верхнего уровня в отдельных файлах *.json. Для *.yaml обеспечить safe_load через зависимость PyYAML при поставке extra. Проверить каталог, тип документов и уникальность stem до построения графа. |
| plugin | factory, options | Доверенная локальная фабрика module:callable из установленного Python-пакета. options — TOML-таблица с JSON-совместимыми значениями. Вызов factory(options) возвращает ContextProvider с describe(), валидной selectors_schema и read-only fetch. Для результата работает serialize(obj) → str. Через эту точку подключаются API, собственные БД, semantic backend и CompositeRelationalProvider. |

Для csv/sqlite вынести загрузчик SchemaConfig из примера в библиотеку, вызывать validate_schema. Встроенный минимум для обоих — schema/query. Публиковать semantic_only и semantic_clauses только для явно сконфигурированного через plugin бэкенда. Для plugin владелец фабрики отвечает за read-only доступ и ограничение работы на стороне источника. Логическое имя в плане всегда равно ключу sources, даже если provider.name отличается. Повторно использовать неизменяемые метаданные можно в пределах процесса.

## Подключение клиентов

Клиент запускает один процесс с абсолютными путями к установленной команде и конфигурации. Для модели с ключом передать именованную переменную в окружение **дочернего процесса** через механизм секретов хоста. Модель внешнего агента и учётные данные его подписки для работы сервера не требуются. При таком подключении клиенту достаточно поддержки MCP tools, включая клиенты без sampling.

Codex (синтаксис проверен через `codex mcp add --help` в CLI 0.167.2):

```sh
codex mcp add fetchgraph -- /opt/fetchgraph/bin/fetchgraph-mcp --config /srv/shop/fetchgraph.toml
```

OpenCode 1.x, файл `opencode.json`:

```json
{"mcp":{"fetchgraph":{"type":"local","command":["/opt/fetchgraph/bin/fetchgraph-mcp","--config","/srv/shop/fetchgraph.toml"],"enabled":true,"timeout":90000}}}
```

Для OpenCode v2 команда регистрации — `opencode mcp add fetchgraph -- /opt/fetchgraph/bin/fetchgraph-mcp --config /srv/shop/fetchgraph.toml`. В конфигурации v2 локальные серверы размещаются под `mcp.servers`. Задать тайм-аут вызова у клиента больше серверного дедлайна в 60 секунд. См. [документацию OpenCode](https://opencode.ai/docs/mcp-servers/).

## Протокол и инструменты

Базовая проверяемая ревизия MCP — 2025-11-25. Использовать lifecycle и согласование версии SDK, дождаться notifications/initialized. Возможности сервера — tools, статический список, listChanged=false. tools/list возвращает четыре описания из tools.json за один вызов. stdout содержит только UTF-8 JSON-RPC, одно сообщение на строку. EOF завершает процесс. Инструменты работают без MCP resources, prompts и экспериментальных tasks. См. [MCP tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) и [stdio](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Успех tools/call содержит isError=false, structuredContent с объектом по outputSchema и один TextContent с компактной JSON-сериализацией того же объекта для клиентов, читающих только текст. Ошибка инструмента использует тот же способ передачи и isError=true. Все строки — Unicode, все длины и смещения текстовых полей считаются в кодовых точках. Вход валидировать строго, без приведения типов, дополнительных ключей и пустого после trim вопроса. Текст источника может содержать инструкции и спецсимволы, передавать его как данные с JSON-экранированием.

| Инструмент | Когда агент его вызывает | Поведение |
|---|---|---|
| fetchgraph_catalog | Обнаружить источники и допустимые для них модели | Аргументы {}. Вернуть описание и алиасы профилей, источники по id в лексикографическом порядке. Читает только настроенный каталог, 0 обращений к данным и модели. |
| fetchgraph_retrieve | Получить данные для рассуждения внешнего агента | Аргументы совпадают с ask. Возвращает EvidenceBundle после PLAN и FETCH, с одним обращением к модели. Выданные ref доступны через read_evidence в этой сессии. |
| fetchgraph_ask | Получить ответ на вопрос | Обязательны source и question. Необязательный inference_profile выбирает профиль из списка данного источника, иначе default_profile. Сначала проверить source, затем наличие и разрешение профиля. В ответе profile — фактически выбранный алиас. |
| fetchgraph_read_evidence | Проверить выдержку или прочитать продолжение | ref берётся из ask. offset по умолчанию 0, length 2048. Вернуть text[offset:offset+length] из сохранённого снимка, selectors фактически выполненного запроса, total_chars и next_offset, равный концу страницы, либо null при достижении конца. При offset=total_chars вернуть пустой текст и null, при большем смещении — INVALID_ARGUMENT. 0 вызовов провайдера и модели. |

### Наблюдаемый обмен

Вызов ask:

```json
{"source":"shop","question":"Сколько заказов в магазине?","inference_profile":"local"}
```

Его structuredContent (ref в примере условный):

```json
{"status":"answered","answer":"В магазине 1000 заказов [1].","profile":"local","evidence":[{"ref":"ev_0123456789abcdef0123456789abcdef","source":"shop","locator":"orders/aggregations/n","preview":"{\"n\":1000}"}],"gaps":[]}
```

После `fetchgraph_read_evidence({"ref":"ev_0123456789abcdef0123456789abcdef"})`:

```json
{"ref":"ev_0123456789abcdef0123456789abcdef","source":"shop","locator":"orders/aggregations/n","selectors":{"op":"query","root_entity":"orders","limit":100,"aggregations":[{"field":"order_id","agg":"count","alias":"n"}]},"text":"{\"n\":1000}","total_chars":10,"next_offset":null}
```

## Выполнение одного вопроса

1. Разрешить source и профиль на сервере. Зарезервировать один из двух параллельных слотов ask, иначе BUSY без очереди. Каждый запрос получает собственные план, кандидаты evidence и дедлайн. Catalog/read доступны, пока работает ask.
2. **PLAN.** Общий async inference-клиент отправляет один POST на base_url + /chat/completions (удалить завершающий slash). Выбрать plan_model для PLAN, synth_model для SYNTH. Передать model, messages, max_tokens=2048, stream=false. Инструкции формата — в system, вопрос и JSON-данные — в user. Извлечь непустой текст первого choices[].message.content. При сетевой ошибке, HTTP-ошибке, пустом либо оборванном по length ответе вернуть MODEL_FAILED. Запросы без автоматических повторов, тайм-аут равен остатку дедлайна. Профиль фиксируется для обеих стадий.
3. Планировщику дать вопрос, описание выбранного провайдера, допустимую схему и пример. Для relational передать также имена таблиц, полей, типов и связей из SchemaConfig. Ответ PLAN — JSON-объект с единственным полем context_plan, массивом ровно из одного объекта {provider,selectors}. provider равен source. Пустой массив означает, что вопросу не соответствует доступная операция, результат insufficient. Другие нарушения структуры — INVALID_PLAN. Единственный шаг в v1 позволяет однозначно связать ответ и фактические селекторы. Использовать ContextFetchSpec и подходящую нормализацию PlanNormalizer для relational. Проверить исходные ключи и окончательный селектор до выполнения, включая результат нормализации. Для ответа, требующего нескольких зависимых операций, планировщику предписать пустой план либо одну операцию для частичного ответа с явным описанием оставшегося пробела. Публичный PlanParser пропускает отдельные повреждённые шаги, для этого входа требуется строгий разбор.
4. **FETCH.** У relational передать вопрос как feature_name и валидированный selectors. Обязателен op. Для query проверить поля, связи, названия сущностей по SchemaConfig, select.expr принимает только поле либо entity.field. Разрешить агрегаты count, count_distinct, sum, min, max, avg, операторы сравнения =, !=, >, >=, <, <=, in, not_in, like, ilike и логические and/or только там, где конкретный backend их реализует. Параметры значений передавать средствами провайдера. limit по умолчанию 100, допустим 1..100, offset 0..10000. Запретить null limit, неизвестные поля на всех уровнях и произвольные выражения. В схему для PLAN включать только исполнимые операции. Собрать корректные ссылки JSON Schema из моделей вариантов, проверить разрешимость $ref (простое вложение независимых Pydantic-схем в oneOf может оставить ссылки на чужой корень).
5. У artifact формат селектора — {family,anchors}. Закрытые варианты: EXPLAIN_TARGET(target_id), EXPLAIN_DERIVATION(source_id,target_id), CASE_DOSSIER(case_id), VALIDATOR_DEFECT_PACK(defect_id,validator_name). Все перечисленные якоря обязательны, непустые строки до 240 символов. Вызвать ArtifactContextProvider.fetch с family как feature_name, anchors как selectors, привязанными run_dir/run_id, deterministic и max_llm_calls=0. Проверять точное совпадение переданных ID, если движок подобрал объект поиском. Результат без точного соответствия считать пробелом. Для plugin строго валидировать selectors по контракту фабрики и вызвать fetch(question, selectors=...). Исключение источника — SOURCE_FAILED.
6. **Свидетельства.** Из результата сформировать упорядоченные пары (locator,text). Для relational сначала агрегаты по имени, затем строки в порядке результата. Для агрегата text — компактный объект {alias:value}, locator — root_entity/aggregations/alias. Для строки — JSON RowResult, locator — entity/rows/index (индекс с нуля в результате данного запроса). Для schema — по одному JSON-описанию на сущность и связь, locator entities/name либо relations/name. Нормализовать NumPy-скаляры через item(), даты в ISO 8601, пропуски в null, бесконечности отклонять. Для artifact брать fragment из EvidenceCapsule и locator из run_id/artifact_id[/fragment_path], обойти selected_evidence, symptom_capsules, upstream_capsules или evidence согласно типу ответа. Считать unresolved_gaps и непустую boundary ограничениями полноты. Для plugin — текст serialize, locator равен id источника. Пути к локальным файлам из внутренних метаданных в locator не возвращать. Символы / и ~ внутри сегментов экранировать по JSON Pointer.
7. Выбрать первые восемь непустых свидетельств, максимум 16384 символа суммарно. Последний текст усечь по оставшемуся бюджету. Любое такое отсечение, пропуск из-за лимита или достижение лимита строк при запросе списка отразить в gaps. Для агрегата без группировки n=0 — полноценное свидетельство. Пустая выборка для запроса конкретной записи даёт insufficient. При отсутствии свидетельств завершить без SYNTH, с пустым evidence и пояснением в gaps. Бюджет 16384 символа учитывает text и компактную JSON-сериализацию data суммарно. Если структурированный payload не помещается, data становится null с явным gap, затем ограничивается текст. Верхние пределы действуют до отправки prompt и записи в кэш. Дополнительная защита тяжёлого ввода: ограничить UTF-8 размер каждого сформированного prompt 96 КиБ до сетевого вызова (BUDGET_EXCEEDED). Встроенные eager-источники csv/artifact предварительно ограничить суммой размеров входных файлов 64 МиБ; для больших таблиц использовать SQLite или pushdown-провайдер. Размер CSV на диске не эквивалентен пику памяти pandas. SQLite ограничивает число возвращаемых строк на стороне БД и учитывает deadline через progress handler.
8. **SYNTH для answer/ask.** Передать вопрос, исполненные селекторы и пронумерованные с 1 тексты. Инструкция модели — опираться на эти свидетельства, возвращать JSON {status,answer,gaps}, явно указывать пробелы и ставить [N] у выводов. answered требует хотя бы одну валидную ссылку и пустой gaps, partial — ссылку и непустой gaps, insufficient — непустой gaps. Каждая ссылка должна указывать на существующий номер. Сервер сам формирует evidence в том же порядке, подставляет preview (первые 240 символов), проверяет границы результата. Сохранить обязательные серверные gaps в ответе, при ограниченном покрытии понизить answered до partial. Если вывод не помещается или нарушает контракт ссылок — INVALID_ANSWER. Ссылка удостоверяет происхождение выдержки; смысловое соответствие вывода проверяется на эталонных примерах. Для ответа без SYNTH использовать «Недостаточно данных для ответа.»
9. Опубликовать снимки и ответ атомарно после последней проверки. Для каждого ref использовать ev_ + 32 случайные шестнадцатеричные цифры. Вместе с текстом сохранить копию переданных fetch селекторов после нормализации и применения серверных ограничений. До fetch проверить размер их компактного JSON в UTF-8 (до 4096 байт, иначе BUDGET_EXCEEDED). Эти селекторы read возвращает на каждой странице, поэтому клиент может проверить фильтры и область агрегации. Снимки хранятся только в памяти текущего соединения, TTL 10 минут по монотонным часам с момента публикации. Вместимость 64 ответа, вытеснение самого раннего ответа целиком, чтение TTL не продлевает. После перезапуска, вытеснения, истечения TTL или для чужой ссылки — EVIDENCE_GONE. Повтор ask выполняется заново, read возвращает ту же строку даже после изменения источника.

Общий RetrievalEngine выполняет PLAN → FETCH и возвращает EvidenceBundle. Convenience answer и MCP ask добавляют SYNTH к полученному bundle. Исполнитель использует общие модели, нормализацию и провайдеров. Это позволяет обойти ограничения публичного run без подмены его приватных методов и без записи через saver. Сформированный контракт не требует refetch, refine, фоновых jobs или отдельного HTTP-сервиса. Любой новый источник регистрируется в конфигурации, список MCP-инструментов при этом фиксирован.

## Ошибки и жизненный цикл

Неизвестный MCP method, повреждённый JSON-RPC и неизвестное имя инструмента обрабатывает протокольный слой SDK. Для известного инструмента ошибки аргументов и исполнения передавать как tool result с объектом error. Код определяет действие клиента, message — краткое пояснение без traceback, путей, секретов и тела запроса к модели. Пример structuredContent:

```json
{"error":{"code":"PROFILE_FORBIDDEN","message":"Этот профиль недоступен для источника shop.","retryable":false}}
```

| Код | Условие и действие клиента |
|---|---|
| INVALID_ARGUMENT | Ошибка полей входа либо смещения страницы. Исправить аргументы. |
| SOURCE_UNKNOWN / PROFILE_UNKNOWN / PROFILE_FORBIDDEN | Источник отсутствует, профиль отсутствует, либо профиль исключён из списка источника соответственно. Перечитать catalog. |
| BUSY / TIMEOUT | Оба слота заняты либо истекли 60 секунд с начала вызова. Повтор допустим. |
| SOURCE_FAILED | Ошибка открытия, чтения, преобразования данных или исполнения у провайдера. После исправления доступности или содержимого можно задать вопрос снова. |
| MODEL_FAILED | Недоступная модель, ошибка авторизации/транспорта, пустой или незавершённый completion. Временные сбои допускают повтор. |
| INVALID_PLAN / INVALID_ANSWER | Ошибка разбора JSON, проверки полей, выбора операции или ссылок соответствующей стадии. Нет повторной генерации внутри этого вызова. |
| BUDGET_EXCEEDED | Превышен лимит исходных файлов, селекторов или prompt, либо невозможно представить обязательные метаданные в пределах контракта. Сузить источник или вопрос. |
| EVIDENCE_GONE | Снимок недоступен для соединения. Для получения нового результата снова вызвать ask. |
| INTERNAL | Непредвиденная ошибка реализации. Скрыть детали от клиента. |

retryable=true для BUSY, TIMEOUT и временной ошибки источника/модели (потеря соединения, HTTP 429 или 5xx). Для остальных случаев false. Истечение общего дедлайна имеет приоритет над ошибкой отдельной стадии. MCP notifications/cancelled привязывается к JSON-RPC request id. Отменить ожидающий ввод-вывод, остановить дальнейшие стадии, отбросить результат. Если синхронный fetch или inference невозможно прервать, выполнять его вне event loop, сохранить занятый слот до фактической остановки; поздний результат никогда не публиковать. При гонке завершение и отмена имеют одну точку фиксации: доставленная раньше фиксации отмена побеждает. Отключение клиента освобождает снимки и завершает работников. Повторный запуск процесса начинает новую сессию.

Для штатной диагностики в stderr достаточно request id, стадии, алиасов источника/профиля, длительности, кода и счётчиков. Не включать содержимое prompt, selectors, фрагменты или ответ. У библиотечного logger есть INFO-сообщения с полным вопросом и селекторами, поэтому настроить фильтрацию также для вложенных логгеров. Хранилище replay/tracer по умолчанию отключено.

## Приёмка

Тестировать установленный wheel в отдельном окружении. Поднять MCP-клиент по stdio, тестовый OpenAI-compatible HTTP endpoint со сценарными ответами и использовать реальные встроенные провайдеры. Сценарная модель позволяет точно посчитать обращения и воспроизвести ошибки. Серия проверок для выпуска:

| Сценарий | Наблюдаемый критерий |
|---|---|
| Установка и обнаружение | Импорт fetchgraph без extra по-прежнему работает. Установка с extra предоставляет команду. Из другого cwd загружается TOML; catalog работает с выключенными БД/endpoint после регистрации путей. Протокольный клиент завершает handshake, получает четыре инструмента, принимает все input/output schemas и читает текстовый fallback. |
| Вопрос по магазину | Для схемы и CSV из примера PLAN выбирает {"op":"query","root_entity":"orders","aggregations":[{"field":"order_id","agg":"count","alias":"n"}]}. SYNTH видит 1000. Ask возвращает answered и ссылку, read возвращает JSON-число 1000, в обеих стадиях отсутствуют все 1000 исходных строк. На стороне модели ровно два POST. |
| Выбор модели | Два профиля с разными endpoint/model. По умолчанию вызваны стадии default_profile, явный алиас переключает обе, plan_model и synth_model попадают в соответствующие HTTP payload. При неизвестном/запрещённом алиасе нет сетевых вызовов. Ни одно сообщение MCP не содержит api_key_env, ключ или URL inference. |
| SQLite и пользовательская фабрика | Та же тестовая таблица даёт тот же агрегат через mode=ro. Фабрика с name, отличным от id, получает только валидированные селекторы и сохраняет работоспособность через alias. Неизвестный столбец, неподдерживаемый агрегат, неизвестный op или попытка выбрать другую БД останавливаются до выполнения fetch. |
| Граф артефактов | По fixture с совпадающими stem/anchors проверить четыре семейства и ID в locator. Отсутствующий точный anchor даёт insufficient с gaps, совпадение только по подстроке не служит доказательством. Read возвращает fragment конкретного run. |
| Недостаток сведений | Проверить пустой context_plan, пустую выборку, нулевой агрегат, частичный ответ, выдуманную ссылку [9] при одном фрагменте, некорректный JSON модели. Отличить доменный insufficient от isError=true; при ошибке ref не публикуется. |
| Большой результат | Ответ с девятью свидетельствами, длинным Unicode-текстом и кавычками укладывается в лимиты, отмечает пропуски. В prompt только допущенные данные. Сборка всех страниц read совпадает с текстом, поданным SYNTH, включая многобайтовые символы. |
| Снимок и гонки | Изменить источник после ask и подтвердить прежний текст по ref. Проверить EOF, TTL, вытеснение 65-м ответом, ref из второго процесса, offset на границе и за границей. Одновременные ask разных источников не смешивают контекст. Третий ask получает BUSY; catalog и read продолжают отвечать. После отмены/тайм-аута нет новых стадий и отложенной публикации. |
| Реальные клиенты | В Codex и OpenCode подключить установленную команду, задать вопрос о магазине, получить 1000, попросить показать свидетельство. Проверить последовательность catalog → ask → read, чистый stdout, отсутствие необходимости копировать CSV или передавать ключ модели в чат. |

Порядок реализации: (1) CLI, конфигурация и catalog с проверкой wheel; (2) источник CSV, inference и сквозной вопрос из примера; (3) ссылки, снимки, чтение и лимиты; (4) остальные адаптеры и сценарии ошибок; (5) приёмка через оба клиента. Совместимость v1 проверять по именам инструментов, схемам, смыслу статусов и неизменности уже выданного снимка.

## Состояние реализации

Общее выполнение и конфигурация реализованы в src/fetchgraph/retrieval. MCP-диспетчер и сессионные снимки реализованы в src/fetchgraph/mcp, инструменты поставляются внутри wheel как package data. HTTP-клиент inference использует httpx и OpenAI-compatible Chat Completions. CI устанавливает extra mcp вместе с dev. Для локальной проверки:

```sh
python -m pip install '.[dev,mcp]'
python -m pytest tests/mcp -q
python -m build --wheel
fetchgraph-mcp --config /absolute/path/fetchgraph.toml --check-config
```

Проверены реальный stdio lifecycle официального SDK, HTTP inference с разными моделями PLAN/SYNTH, CSV-агрегация 1000, чтение снимка, SQLite-агрегация 0, четыре семейства artifact, plugin с отличающимся именем, отклонение опасных селекторов и неверных ссылок, Unicode-пагинация, TTL и отмена синхронного fetch с удержанием слота. Сквозной тест также выполнен на установленном wheel вне checkout. Проверка типов выполняется с --pythonversion 3.11, поскольку общий pyrightconfig проекта пока указывает Python 3.10.

В общем прогоне остаётся исходный сбой examples/demo_qa/tests/test_demo_qa_compare_resolver.py::test_latest_prefers_newer_effective_ts_over_source_rank. Он воспроизведён на исходном HEAD 1b49f5c в отдельной распакованной копии. При подготовке коммитов pytest-hook пропущен после явного выполнения тестов.

Проверка в интерактивных Codex/OpenCode с настоящей моделью пока не выполнена. Конфигурационные примеры приведены выше, протокольная интеграция проверена клиентом MCP SDK. Синхронные пользовательские провайдеры должны самостоятельно ограничивать длительность операций ввода-вывода, поскольку Python-поток с выполняющимся fetch удерживает слот до фактического завершения.


После выделения Retrieval API дополнительно проверены Python retrieve/aretrieve, answer, выбор источника, конфигурация через FETCHGRAPH_CONFIG, round-trip EvidenceBundle и импорт базового пакета без загрузки MCP/inference-зависимостей. В установленном wheel один HTTP-тест проверяет MCP retrieve → read → ask и отдельный Python retrieve. Для retrieval наблюдается ровно один вызов PLAN, для ask — PLAN и SYNTH. В Python bundle сохраняются исходные JSON-данные provider даже при кратком serialize().
